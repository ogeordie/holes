## DESCRIPTION
This code was used to run the simulations described in the articles "Size Matters:
Determining Optimal Test Pit Size for Dispersed Archaeological Test Excavation Programs"
(in preparation) and "Layout Matters: Determining Optimal Test Pit Layout for Dispersed
Archaeological Test Excavation Programs" (submitted to Journal of Archaeological Science)
by Geordie Oakes and Andrew McLaren.

Only "Layout Matters" experiments are currently supported. "Size Matters" details are
included in this document for future reference.

The file `LayoutExperiments.py` initiates the experiments which save data to `csv` files.
It then triggers graphs and tables to be produced using these data.

The program places square test pits ("holes" in the code) of given number and size on a square field 
of a given size. The field has a randomly placed archaeological site (referred to as both
"treasure" and "site" in the code), specified either by a circle, rectangle, or arbitrary
polygon (for intersection experiments), or by real-world data on artefact distribution from
digs in NSW Australia (for detection experiments in "Size Matters"). See the
`real world site specifications` directory for the real-world data csv files. See the
`case studies site specifications` directory for the polygon `shapefile` definitions
(in `zip` files). The rectangle and polygon treasures can be oriented in any direction,
however in the experiments this value was usually between 0 (horizontal) and 90
(vertical) degrees (as higher orientations did not produce significantly different
results, for example 30 degree results were similar to 180 minus 30 = 150 degree results).

The design of Holes is as follows. See `HolesCoreUML.png`, `TreasureUML.png`,
and `ExperimentsUML.png` for UML diagrams. An `ExperimentRunner` is given an
`Experiment`, which defines all parameters of an experiment (such as field size and
hole size). When `ExperimentRunner.runExperiment()` is called, it runs several
thousand iterations for each number of holes (incrementing the number of holes until
100% success rate is reached - see below). The number by which holes are incremented
each time is specified by the `Experiment`. In each of the several thousand iterations,
the `ExperimentRunner` creates a `Field`, gets a `Treasure` from the `Experiment`'s
`TreasureManager`, and places the `Treasure` randomly on the `Field`. It gets a
`Player` from the `Experiment`, providing it with the `Field` and desired number of
holes to dig. It calls `Player.play()` to perform an archaeological dig, which digs
`Hole`s on the `Field` (by calling `Field.digHole(size, centre)`) according to its
layout algorithm. The `ExperimentRunner` notes whether or not the dig was successful
(found treasure - returned by `Field.digHole()` which calls `Treasure.intersectsHole(hole)`),
and how many holes were dug by the `Player`'s layout algorithm (which may differ from
the desired number of holes due to details of the layout algorithm). After all
the iterations, it records the success rate for that number of holes in a `csv` file
whose name is determined by the `Experiment` in subdirectories of the `data`
directory. So at the end of the experiment, the `csv` file contains success rates
over a range of numbers of holes. Graphs and Tables are then generated by calling
functions in Plotter.py, which are stored in subdirectories of the `graphs` directory.

The different treasure types are implemented in subclasses of the abstract `Treasure`
class (and are created by the corresponding `TreasureManager` implementations).
In particular there is a `RandomisedTreasureManager` which supplies a `RectangularTreasure`
that has a random area, length, and orientation, and so is different on each simulation
iteration. The other `TreasureManager`s are straighforward. Having a `TreasureManager`
class allows layout algorithms (`Player`s) and `Treasure` specifications to be mixed
and matched when creating an `Experiment`. For "Layout Matters" experiments, when
`Treasure.placeRandomly()` is called by the `Field`, it positions itself so that
at least two thirds of at least two sides of the treasure's bounding box lies within
the `Field`. Behaviour for "Size Matters" experiments is not yet decided.

Different layout algorithms are implemented by subclasses of the abstract `Player` class.
Layout algorithms are implemented as follows:
- Hexagonal-like by the `HexagonalLikePlayer`
- StaggerXY by the `HexagonalLikePlayer` with appropriate arguments to its constructor
  (staggerY = True).
- RandomisedStaggerXY by the `HexagonalLikePlayer` with appropriate arguments to its
  constructor (staggerY = True, randomise = True).
- Halton by `HaltonPlayer`
- Random by `RandomPlayer`
- `HexagonalPlayer` was used to test if it had similar performance to the
`HexagonalLikePlayer`, which it did for the most part (for some treasure elongations
and orientations `HexagonalLikePlayer` performed slighlty better).

Note that the layout algorithms enforce a border at the edges of the `Field`
where no holes are dug. This is usually 1/4 of the distance between holes in
a row for left and right borders, and 1/4 of the distance between rows for
top and bottom borders. Random and Halton use margins that would be used on
a square grid layout (with margins) with the same number of holes.

See the document `size matters and layout matters layout algorithms.pdf`
for details of the layout algorithms.

The inner simulation procedure is run 10000 times for each number of holes in "Size Matters"
(i.e. there are 10000 digs for each number of holes), with the treasure placed randomly each
time. In "Layout Matters" the procedure is run 8000 times for success experiments and 4000
times for summary experiments (see [LAYOUT MATTERS EXPERIMENTS](#LAYOUT-MATTERS-EXPERIMENTS)
below for descriptions of these). The lower number is used for summary experiments as
the experiments take a very long time and for summary purposes this suffices. For smaller
numbers of holes the procedure is run 15000 times as there is more variation in results.
The output of an experiment is, for each number of holes, the desired number of holes, the
actual number of holes as determined by the layout algorithm (which may differ from the
desired number of holes due to layout algorithm constraints), and the percentage of runs
where a hole found treasure ("success rate"). These data are printed to standard output
(optionally) and saved to a csv file.

As mentioned above, note that some players dig a different number of holes than the 
one supplied to them as the layout algorithm may not work with all numbers of holes. This 
actual number of holes is also returned by `Player.play()` (as well as whether the dig was
successful). `Player.play()` has an argument `returnAfterHit` which if `True` will cause
the method to return as soon as treasure if found. However note that the actual number of
holes returned is the number of holes that would have been dug if `returnAfterHit` was
`False` (i.e. the number of holes determined by the layout algorithm).

The main file is `LayoutExperiments.py` for "Layout Matters" experiments.
These files trigger the various experiments and the generation
of graphs and tables. Note that one can set the "go" variables in these files to
control what is triggered, for example if one wishes to use pre-generated data rather
than generating it which can take over 16 hours on a fast computer for "Layout Matters"
experiments (excluding the "supplemental" experiments not included in the paper
which can take over 72 hours).

As well as running the simulations as described above, there is
also the functionality to save a field (with holes and treasure) to a text file, by
calling `ExperimentRunner.printExperiment()` (which can also be triggered from
`SizeMattersExperiments.py` and `LayoutExperiments.py` by setting `goPrintExperiments`
to `True`). Printed experiments are saved to `hpf` files (for Holes Printed Field)
in the `printedFields` directory. 
The file `CreateFieldImage.py` contains code to read printed field `hpf` files
and produce graphical representations of the fields, useful in debugging.
This module works in two modes: `allNewHPFFiles` and `onlyNamedFile`. The former mode
displays and creates `png` files for any `hpf` files in the `printedFields` directory
that don't have a more recent corresponding `png` file. Each window displayed must be
closed individually to cause the file to be saved. The latter mode displays
and creates a `png` file for the file named in the global `filename` variable.
The mode is set by changing the global `mode` variable. Both these variables are
near the top of the `CreateFieldImage.py` file.

See the [FILES](#FILES) section below for information on other files.

The inner simulation procedure (called thousands of times for each number of holes) is simplified
as (for example):
```
field = Field(fieldSize, fieldSize)
treasure = experiment.getTreasureManager().getTreasure()
field.placeTreasure(treasure)
player = experiment.getPlayer(field, numberOfHoles)
result = player.play()
if result[0]:
    # player found treasure
    successes = successes + 1
# layout algorithm decided to dig this number of holes:
actualNumberOfHoles = result[1]
```
Then after the many iterations, the output is `number of holes`,
`actualNumberOfHoles`, and `successes * 100 / <number of iterations>` which is the
success rate. (We assume `actualNumberOfHoles` will be the same when `number of holes`
is the same). The output is saved to the file specified in the `Experiment` subclass.

The code defines the top left of the field as the origin (0,0), and defines horizontal
treasure orientation as 0 degrees and vertical as 90 degrees.

The code was only tested with the experiments explored in the articles. It 
may not be correct in all circumstances.


## INSTALLATION AND RUNNING

There are two ways to get the code: from Zenodo or GitHub.
The GitHub repository is https://github.com/ogeordie/holes.

There are many ways to view, edit, and run a Python script, too many describe each one.
In particular, one can use an Integrated Development Environment (IDE) or run instructions
from the command line.
Below are instructions using VSCode (a popular and freely available IDE that runs on
Windows, MacOS, and Linux), and also instructions using the command line in a bash
environment under Debian Linux (including Ubuntu), bash under macOS, and the Command
Prompt under Windows. We trust that these instructions can be adapted to the setup of
your choice.

The code was developed and tested with Python 3.13 (as the kivy library did not support 3.14
at time of writing). While the core code (excluding dependencies) will probably work with
later versions, revert to 3.13 if there are any issues. 

### VS Code Instructions
1.  Follow the steps in this tutorial 
    https://code.visualstudio.com/docs/python/python-tutorial
    to install Python 3.13, VS Code, and the VS Code Python extension. Be sure you install the
    Python extension from the VS Code Extension Marketplace (see
    https://code.visualstudio.com/docs/configure/extensions/extension-marketplace) and search
    for Python.
    Note that Python 3.13 was used during development of this code.
    Note that while the tutorial says "The system install of Python on macOS is not supported"
    we have found that it does in fact work (downloading from https://python.org/downloads/macos/).
    However if it doesn't work for you use "brew" as the tutorial suggests.

2.  Continue with steps in that tutorial to create a workspace folder, e.g.
    `C:\programming\holes` (for Windows) and open that folder in VS Code. Avoid spaces in the
    folder path.

3.  Place the python files and the other files and folders from the repository in that folder.
    If using GitHub, you can use it to manage your code if you
    like, including VS Code GitHub integration (but we have not tested this). We have included
    the `.venv` folder in the `.gitignore` file - see step 4. Otherwise you can simply download the
    files in the repository as a zip file from GitHub or Zenodo, unzip them, and copy them
    to your directory (be sure the files and folders are in the folder you opened with VS Code).

4.  Continue with steps in the tutorial to create a virtual Venv environment using the
    VS Code `Python: Create Environment` command (with the folder open in VS Code).
    You will need to select the Python version to use in the environment, which should
    be 3.13.x. Select `venv` for environment type. If asked, skip installation of dependencies
    (they are installed in step 5 below). This virtual environment will avoid installed dependencies
    from conflicting with other projects. 

5.  With the folder open, create a `New Terminal` from the `Terminal` menu (**NOTE: it is important that
    a new terminal is created after creating the virtual python environment. Make sure the prompt
    begins with `(.venv)`**). Run `python --version` which should show 3.13.x. Then install dependencies
    of Holes in the VS Code terminal by running:
    ```
    python -m pip install -r requirements.txt
    ```

6.  Run the code! With `LayoutExperiments.py` open in the editor (click it in the
    Explorer bar on the left of the VS Code window),
    press F5 to debug or Ctrl-F5 to run (or select the option from the Run menu).
    If you are asked to choose debugger choose "Python Debugger".
    If you are asked for a "Debug Configuration" choose "Python File". It is more efficient
    to "run" the program rather then "debug".

Whenever you run commands from the VS Code Terminal, make sure the command prompt begins with `(.venv)`.
If it doesn't, create a `New Terminal` from the `Terminal` menu. If that doesn't work you may
have missed creating a virtual environment in step 4 above for the folder that's open in VS Code.


### Command Line Instructions
1.  Install python environment

    - Using bash under Debian Linux:
        ```
        sudo add-apt-repository ppa:deadsnakes/ppa
        sudo apt update
        sudo apt install python3.13
        sudo apt install python3-pip
        sudo apt install python3.13-venv
        ```

    - On macOS install latest python 3.13 from https://python.org/downloads/macos/

    - On Windows install latest python 3.13 from https://www.python.org/downloads/windows/
    (**NOTE: tick the box to add python.exe to your PATH**)

2.  Create a directory (e.g. `~/programming/holes` on Linux and macOS or `C:\programming\holes` on Windows),
    place the files and folders from the repository in it, and `cd` to it. Make sure the directory you
    are in contains the python files and all the other files and folders from the repository.

3.  Create and activate a python virtual environment
    - On bash using macOS Terminal or Linux (run `bash` if it is not the default shell):
        ```
        python3.13 -m venv .venv
        source .venv/bin/activate
        pip3 install -r requirements.txt
        ```

    - On Windows Command Prompt, use the `py` loader to select the correct version (3.13):
        ```
        py -3.13 -m venv .venv
        .venv\Scripts\activate
        pip install -r requirements.txt
        ```

    The prompt should now begin with `(.venv)`, indicating that
    the virtual environment has been activated.

4.  Run the code. Confirm that `python --version` shows 3.13.x. Also ensure
    you have activated the virtual environment (`source .venv/bin/activate` on bash
    or `.venv\Scripts\activate` on Windows Command Prompt). Then run:
    ```
    python LayoutExperiments.py
    ```
    for "Layout Matters" experiments.

    Note that `"go"` variables can be set in these files to control what they do.
    By default they produce the graphs and tables using pre-generated data,
    but this can be changed to create the data from scratch (for
    LayoutExperiments.py this can take over 16 hours on a fast computer, and
    for SizeMattersExperiments.py over 1 hour and 45 minutes).

5. To deactivate the virtual environment:
    ```
    deactivate
    ```
    Be sure to `activate` it again before running the program again. You need to `activate` it
    each time your shell or command prompt is started (the prompt should begin
    with `(.venv)` when the virtual environment has been activated).


### Printing and Viewing Fields
To create a graphical image of a field, you first print the field to the
`printedFields` directory (e.g. by setting `goPrintExperiments` to `True` in
`LayoutExperiments.py` and running the file).
Printed fields are saved in `hpf` files. Example printed field files and
corresponding `png` files for "Layout Matters" experiments exist in the
`printedFields` directory.
`CreateFieldImage.py` runs in two modes as described above and in the file
comments. Edit the mode and file name as desired near the top of the file and run:
`python CreateFieldImage.py` if using the command line instructions, or run the file
in VS Code. This will display the images and also save them as `png` files in the
`printedFields` directory.


## DEPENDENCIES

Dependencies are listed in the `requirements.txt` file for easy installation, and their
licenses are available (in the `site-packages` directory somewhere in `.venv` subdirectories)
once they have been installed.

The Kivy framework (version 2.3.1) is used in `CreateImageField.py` to graphically display a field
for debugging purposes.

The sciPy library (version 1.16.3) is used by the HaltonPlayer in `Players.py` to generate
scrambled Halton distributions.

The numPy library (version 2.3.4) is used in `Tables.py`, `Plotter.py`, and `Players.py`.

The matplotlib library (version 3.10.7) is used in `Plotter.py` to produce graphs and tables.

The rich library (version 14.2.0) is used in `SizeMattersExperiments.py` and `LayoutExperiments.py`
to generate progress bars.

The PyShp library (version 3.0.2.post1) is used in `Treasure.py` to read treasure polygon shapes
in the `shapefile` format (usually a `zip` file containing the shape description).
See https://en.wikipedia.org/wiki/Shapefile.

The Shapely library (version 2.1.2) is used in `Treasure.py` to manage polygon
treasures and detect intersection with a hole.

The versions given are those used during development. Newer versions
will probably work but use the stated versions if you run into issues.
Kivy may not support installation of previous versions, so remove the "==2.3.1" 
from the `requirements.txt` file if there is an error during installation.

## LAYOUT MATTERS EXPERIMENTS

These experiments compare various layout algorithms in various ways. The treasures (sites)
are rectangles with various elongation ratios, e.g. 1:1 (square),
5:1, 20:1, etc. The rectangles are oriented from 0 degrees (horizontal) to 90 degrees
(vertical) in most experiments. Additionally more complex polygon shapes are used as case
studies (whichare also rotated to various orientations).

Generated data is stored in various subdirectories of the `data` directory. Raw data on success
of a layout algorithm over a range of numbers of holes are stored in files named:
`<treasure-width>x<treasure-height>@<orientation>rectangle <layout-algorithm> fieldsize<field-size> siteArea<site-area>.csv`.
For case study site shapes (polygon) experiments the data are stored in files named:
`casestudypolygon <description>@<orientation> <layout-algorithm> fieldsize<field-size>.csv`.

The success graphs (`success`, `randomtreasure`, `casestudies`) use these data. The summary graphs
(`summary`, `smallnumholes`) are generated by analysing these raw success data and generating
files named
`summary orientation<orientation> fieldsize<field-size> siteArea<site-area> maxholes<maximum-holes>.csv` in
the `summary` and `smallnumholes` subdirectories of the `data` directory. These are then used
for plotting summary graphs. The summary "rotation" graphs are also generated by analysing the raw
success data, producing files named
`rotation ratio<elongation-ratio> fieldsize<field-size> siteArea<site-area> maxholes<maximum-holes>.csv`
in the `rotation` subdirectory of the `data` directory.

Tables are saved both as `.png` images and `.csv` files.
